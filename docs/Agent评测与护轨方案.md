# Agent 评测与护轨方案

更新：2026-09-15。

## 目标与原则

评审不以“模型是否说得像”为唯一标准，而以可复现证据判断：任务是否完成、工具是否合规、输出是否安全、需求是否符合。护轨采用纵深防御；敏感词只用于发现信号，不能单独充当安全边界。

## 当前实现

| 层 | 当前机制 | 判定方式 |
| --- | --- | --- |
| 输入评审 | Unicode 归一化后的注入/破坏指令分类 | 仅“覆盖指令 + 受保护目标”或破坏命令阻断；单独覆盖语句只告警并审计。 |
| 上下文隔离 | 用户请求、持久记忆、源码和工具结果使用明确的数据边界 | Agent 提示词要求它们只提供事实，不授予新权限。 |
| 执行约束 | 工具白名单、路径/大小限制、修改 Agent 无命令权限、构建沙箱 | 实际调用由代码校验，而非相信模型声明。 |
| 输出评审 | 构建、结构、敏感值/危险调用扫描；可选视觉模型评估需求符合度 | 结果、问题和证据持久化到交付评估。 |

“阻断”只用于高置信度风险；告警保留原始片段和规则名，供管理员复核。误判时应先将样本标注为误报，再调整规则的组合条件或提示词，禁止直接放宽工具权限。

## 如何衡量效果

离线评测分为三个目标，不能混成一个分数：

| 目标 | 数据与指标 | 发布门槛 |
| --- | --- | --- |
| 输入/输出安全 | 对抗、混淆、正常引用样本；高风险召回率、正常需求误阻断率 | 当前基线要求高风险样本零漏检、正常样本零阻断。 |
| Agent 行为 | 固定项目快照下的工具选择、参数和轨迹；违规调用率、任务完成率、无效循环率 | 不得新增越权调用或破坏既有通过轨迹。 |
| 交付质量 | 构建成功、交互证据、视觉/人工需求符合度；按 HTML/Vue 和任务复杂度分组 | 与上一提示词/模型版本做同集对比，不以单次分数发布。 |

`backend/evals/agent_review_cases.json` 是输入评审的确定性回归集，`pytest` 会同时验证结果和两项核心指标。现有 `agent_regression_cases.json` 继续覆盖路由与提示词契约。每个样本应保存类别、输入、预期动作、风险等级和来源；线上经脱敏并人工确认的失败案例优先进入该集。

## 提示词优化闭环

1. 记录失败运行的请求、规则命中、工具轨迹、构建/评审结果和人工标签，不记录密钥。
2. 按“漏检、误报、工具违规、任务未完成、质量不足”归类；先修确定性策略或工具权限，再调整提示词。
3. 将最小可复现案例加入相应回归集；提示词、模型或工具策略改动必须跑全量离线集并与基线比较。
4. 对需求符合度这类主观指标，采用独立视觉/LLM Judge 加人工抽检；Judge 只给建议和排序，不直接授予写入、发布或外发权限。

## 后续演进

优先补齐真实模型的固定工作区轨迹集和管理员评审队列；再引入版本化实验报告（提示词版本、模型、数据集版本、指标）。这与主流 Agent 平台的“最终结果、工具轨迹、单步决策”分层评测一致，但先保持本地 JSON + pytest，避免在当前阶段引入外部评测平台和额外密钥。
